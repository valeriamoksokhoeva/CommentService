# Comment Service

Сервис постов и комментариев на GraphQL, по типу комментариев на Хабре или Reddit. Написан на Go.

Что умеет:

- создавать посты и смотреть их список;
- писать комментарии и отвечать на комментарии, вложенность не ограничена;
- отдавать комментарии постранично;
- присылать новые комментарии подписчикам (GraphQL Subscriptions);
- давать автору поста запретить комментирование.

Данные можно хранить в памяти или в PostgreSQL, это выбирается при запуске.

## Быстрый старт

С PostgreSQL (так проще всего, всё поднимается одной командой):

```bash
docker compose up --build
```

Сервис будет на http://localhost:8080/. Там открывается GraphQL Playground, сами запросы идут на `/query`.

Без базы, данные в памяти и пропадут после остановки:

```bash
go run ./cmd
```

То же самое в Docker:

```bash
docker build -t comment-service .
docker run -p 8080:8080 -e STORAGE=memory comment-service
```

### Настройки

Всё задаётся переменными окружения.

| Переменная | Что делает | По умолчанию |
|---|---|---|
| `STORAGE` | `memory` или `postgres` | `memory` |
| `DATABASE_URL` | адрес PostgreSQL, обязателен при `STORAGE=postgres` | нет |
| `PORT` | порт сервера | `8080` |
| `TEST_DATABASE_URL` | база для интеграционных тестов, см. раздел про тесты | нет |

В `docker-compose.yml` для приложения по умолчанию стоит `STORAGE=postgres`. Значения для compose лежат в `.env`, пример в `.env.example`.

### База и миграции

Таблицы создаёт файл `migrations/001_init.sql`. Compose подключает папку `migrations/` к контейнеру Postgres, и скрипт выполняется один раз, когда база создаётся с нуля. Само приложение миграции не запускает.

Чтобы начать с чистой базы:

```bash
docker compose down -v
docker compose up --build
```

`-v` удаляет том с данными, так что база обнулится.

Если подключаетесь к своей пустой базе, выполните `migrations/001_init.sql` вручную, например через `psql -f`.

## Примеры запросов

Все примеры можно вставлять прямо в Playground. `<POST_ID>` и `<COMMENT_ID>` берите из ответов предыдущих запросов.

Создать пост:

```graphql
mutation {
  createPost(input: { message: "Первый пост", author: "alice", canComment: true }) {
    id
  }
}
```

Написать комментарий:

```graphql
mutation {
  createComment(input: { postId: "<POST_ID>", message: "Комментарий", author: "bob" }) {
    id
  }
}
```

Ответить на комментарий: то же самое, плюс `parentId`:

```graphql
mutation {
  createComment(input: {
    postId: "<POST_ID>"
    parentId: "<COMMENT_ID>"
    message: "Ответ"
    author: "alice"
  }) {
    id
  }
}
```

Список постов:

```graphql
query {
  posts { id message author canComment }
}
```

Пост и комментарии под ним:

```graphql
query {
  post(id: "<POST_ID>") { id message canComment }

  comments(postId: "<POST_ID>", limit: 10, offset: 0) {
    id
    author
    message
    replies {
      id
      message
      replies { id message }
    }
  }
}
```


Глубину ответов выбирает клиент: сколько рaз вложил `replies { ... }`, столько уровней и получит.

Запретить комментарии (может только автор поста):

```graphql
mutation {
  disableComments(postId: "<POST_ID>", author: "alice") { id canComment }
}
```

Подписаться на новые комментарии поста. Работает через WebSocket: откройте Playground в двух вкладках, в одной запустите подписку, в другой создайте комментaрий.

```graphql
subscription {
  commentAdded(postId: "<POST_ID>") { id parentId author message }
}
```

## Правила и ограничения запросов

- Текст комментария не пустой и не длиннее 2000 символов. Считаются именно символы, а не байты, так что кириллица считается честно. Эту же границу проверяет `CHECK` в базе.
- У поста и комментария должны быть непустые текст и автор. Строка из одних пробелов считается пустой.
- `limit` для `comments` от 1 до 100, `offset` не меньше 0. Иначе вернётся ошибка `invalid pagination`.
- Комментировaть можно только существующий пост, на котором комментарии не запрещены. Родитель ответа должен существовать и принадлежать тому же посту.
- Подписаться можно только на существующий пост.

Ошибки приходят в стандартном поле `errors` GraphQL. Тексты ошибок лежат в `internal/domain/errors.go`.

## Как устроен проект

```text
cmd/main.go              запуск, выбор хранилища, настройка сервера
graph/                   схема GraphQL, резолверы (часть файлов генерирует gqlgen)
internal/domain/         модели и ошибки
internal/store/          интерфейс Repository, реализации memory и postgres
internal/subscription/   рассылка новых комментариев подписчикам
migrations/              SQL
```

Резолверы работают только с интерфейсом `store.Repository`, поэтому им всё равно, где лежат данные.

## Как хранятся комментарии и как работает пагинация

Комментарий хранится одной строкой: `id`, `post_id`, `parent_id` (у корневого `NULL`), `message`, `author`, `created_at`. Вложенность задаётся ссылкой на рoдителя.

**Пагинация считается по корневым комментариям.** `limit: 10` значит «до десяти корневых комментариев вместе со всеми их ответами». Корни сортируются по `(created_at, id)`.

В PostgreSQL дерево достаётся одним запросом через `WITH RECURSIVE`: сначала берётся нужная страница корней, потом к ним подтягиваются все потомки. Так что запрос на каждый уровень вложенности не нужен и проблемы N+1 нет. Дерево потом собирается в Go по `map`, за линейное время. Для быстрого выбора корней есть частичный индекс по `(post_id, created_at, id) WHERE parent_id IS NULL`, для обхода потомков индекс по `parent_id`.

В памяти используются три `map`: посты, комментарии по `id` и список `id` комментариев каждого поста. Доступ защищён `sync.RWMutex`.

### Гонка при запрете комментариев

Если автор запрещает комментарии в тот момент, когда кто-то пишет комментарий, комментарий не должен проскочить после запрета. В PostgreSQL `CreateComment` идёт в транзакции и читает пост с `FOR SHARE`, а `UPDATE` при запрете ждёт, пока такие транзакции завершатся. В памяти то же самое решает общий мьютекс. Для этого есть тесты, которые гоняют запись и запрет параллельно.

## Подписки

Подписчики хранятся в `SubscriptionManager` по `id` поста. После успешного создания комментария менеджер раскладывает его по каналам подписчиков этого поста. У каждого подписчика канал на 16 сообщений, так что медленный клиент не тормозит остальных. Если клиент отвалился или отменил подписку, его канал удаляется. Для WebSocket включён keep-alive (пинг раз в 10 секунд).

## Что здесь сделано проще, чем в настоящем сервисе

- **Нет авторизации.** Автор передаётся строкой, и запрет комментариев просто сравнивает её с автором поста. Любой может назваться автором. В реальном сервисе пользователя надо брать из токена.
- **Подписки могут терять сообщения.** Если у клиента забился буфер на 16 сообщений, новые для него пропускаются. Пропущенное можно дочитать обычным запросом `comments`.
- **Подписки работают только внутри одного процесса.** Несколько экземпляров сервиса друг про друга не знают. Для этого нужен брокер вроде Redis или `LISTEN/NOTIFY` в Postgres.
- **Ветка грузится целиком.** Пагинации ответов нет, и очень большая ветка вернётся одним куском, даже если клиент попросил только пару уровней. Решение на будущее: отдельное поле `replies(limit, offset)`.
- **В памяти дерево собирается заново на каждый запрос** и обходит все комментарии поста. Для тестового задания нормально, для большого поста нет.
- **У постов нет пагинации и даты создания.** Список постов в памяти приходит в произвольном порядке. У комментариев тоже нет `createdAt` в API.
- **Часть ошибок базы уходит клиенту как есть.** Не всё приведено к понятным ошибкам.
- Пагинация через `offset`: на очень больших страницах это медленно, правильнее было бы курсором.

## Тесты

Для проверок нужен Docker Desktop (или работающий Docker Engine). Все тесты можно запустить одной командой:

```bash
make test
```

Команда сама:

1. Запускает PostgreSQL в Docker и ждёт его готовности.
2. Создаёт отдельную базу `comments_test`, если её ещё нет.
3. Запускает тесты из всех пакетов. PostgreSQL-интеграционные тесты применяют `migrations/001_init.sql` к тестовой базе автоматически.

Отдельно проверить только PostgreSQL-хранилище можно командой:

```bash
make test-postgres
```

`make test` и `make test-postgres` читают настройки из `.env`. Если файла `.env` нет, создайте его из примера:

```bash
cp .env.example .env
```

Важно: `TEST_DATABASE_URL` должна указывать на отдельную базу `comments_test`, а `DATABASE_URL` — на базу приложения `comments_db`. Интеграционные тесты используют только `TEST_DATABASE_URL`, поэтому тестовые данные не должны попадать в базу приложения.

Для запуска только тестов без автоматического запуска Docker можно выполнить `go test ./... -count=1`, предварительно настроив переменные окружения. Если `TEST_DATABASE_URL` не задана, PostgreSQL-интеграционные тесты будут пропущены. Флаг `-count=1` отключает кеширование результатов тестов.
